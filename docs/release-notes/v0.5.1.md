A deployment release. The machine that holds the collection can now run this as
a container and update itself from GitHub with one command, on a NAS that has no
git and cannot get one.

**The `mm` binaries in this release are the same program as v0.5.0.** No Go
source changed — everything here is the tooling around it. Upgrading is worth it
only if you want the container path; a working v0.5.0 install has nothing to
gain.

## Running the library on a NAS

TOS and DSM ship without git and block the package that would install it, so the
NAS never clones. `nas-update.sh` fetches the branch as a source tarball from
GitHub's REST API, builds the image and restarts the container. That download
*is* the sync — GitHub stays authoritative and the NAS holds no git state to
drift out of date.

The build needs a Go toolchain and nothing else. The web UI is committed under
`internal/webui/dist` and embedded by the compiler, so no Node ever runs on the
NAS.

From a desktop, `nas-refresh.bat` triggers the whole thing over SSH.

Per-box paths and host names live in a settings file outside the repo, not in
the script. Two reasons: this repo is public, and somebody's volume layout has
no business in it; and the update replaces its own directory with `--delete` on
every run, so anything kept inside is overwritten by the next update.

See [`docs/nas-deployment.md`](../nas-deployment.md) for the full runbook.

## Four things the deployment has to get right

Each of these was found by running the thing on real hardware rather than by
reading the code, and each is now handled rather than left to be rediscovered.

**Bridge networking hides who is calling.** Docker's userland proxy rewrites the
source address of every published connection to the bridge gateway, so the
daemon sees `172.17.0.1` for every client no matter how they connected. Every
decision made from the caller's address then collapses: `--tailnet` never
matches, and the only `--trust-cidr` that would satisfy it is the whole bridge —
which exempts every host that can reach the port while reading as though it
exempted only the tailnet. That is the worst kind of security setting, one that
looks narrow and is not. The deployment uses `--network host` for that reason,
not for speed.

**The daemon rejects host names it was not told about.** `ALLOW_HOSTS` must list
every name the UI is opened by. This is the DNS-rebinding defence and the daemon
cannot know its own names, so a missing entry looks exactly like the server
being down — the connection succeeds and every request is refused.

**The state directory needs room for a whole model.** A download is written
there in full and only then moved to its model folder, so a 12 GB fetch needs
12 GB free in two places at once.

**Container paths become permanent database state.** The scanner records the path
it walked, so a model found at `/models` is stored as `/models` for the life of
the library. Where the mount comes *from* can change; where it lands cannot.

## Two ways this could have eaten something

**The deploy directory is not `$HOME/model-manager`.** That is the name the
convention would suggest, and it is also exactly where a working checkout of the
same project tends to live — and the update replaces that directory wholesale.
It uses `$HOME/model-manager-deploy`, and refuses outright if it finds a `.git`
under `APP_DIR`. Naming is the first defence and the refusal is the second,
because the mistake is unrecoverable and only visible afterwards.

**A second model mount is optional and off by default.** Every mounted root is
somewhere the daemon may write, because a download or an archive intake can be
sent to any enabled root. Pointing that at a directory another tool owns and
prunes — a sync tool's versioning folder being the obvious candidate — means what
this daemon captures as a permanent archive, that tool is free to delete. The
archive guarantee is only as good as the directory holding it.

Indexing such a folder is still fine: add it, scan, then disable it. A disabled
root keeps its paths and records but leaves the destination list.

## Smaller fixes

- **Docker is resolved by path, not by `PATH`.** On TOS the engine lives under
  the apps directory and only a login shell picks it up. The remote trigger runs
  a non-login shell, so a bare `docker` was not found there — a bug that worked
  every time it was tested by hand and failed every time it ran the convenient
  way.
- **The updater hands over to its newly installed copy in the same run.** It
  re-execs from a copy of itself at the start, so the logic running during an
  update was always the version installed *before* the fetch. A change to how the
  container runs took two invocations to land, with the first reporting success
  while ignoring the fix it had just downloaded.
- **Shell and batch line endings are pinned.** One carriage return in
  `nas-update.sh` makes `/bin/sh` read `set -eu\r` and fail with `: invalid
  option`, naming neither the file nor the cause.

## Upgrading

Nothing to run by hand, no schema changes, and the daemon is unchanged. If you
already run v0.5.0 outside a container, there is no reason to upgrade.
